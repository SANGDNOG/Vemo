# 모바일 전사 타임라인

Android 전사 탭은 A Native White의 흰 배경, 얇은 구분선과 여백을 유지하며 문장별로 표시한다. 시간 정렬이 있는 문장은 왼쪽에 보라색 시간 표시를 둔다. 시간이 없는 기존 결과는 문장만 구분하며 추정한 시간을 만들지 않는다. 원문은 바꾸지 않는다.

## 선택적 전송 파일

기존 `results/<recording_id>/<audio_sha256>/result.json` v1의 필드는 유지한다. 같은 폴더의 `transcript-timeline.json`을 지원하는 클라이언트만 추가로 읽는다. 기존 클라이언트는 기존 결과를 계속 읽을 수 있다.

파일 필드:

- `schema_version`: 1
- `recording_id`, `audio_sha256`, `processor_id`: 원래 결과의 식별자
- `transcript_sha256`: `result.transcript`의 정확한 UTF-8 바이트 SHA-256
- `segments`: `{ "start": 0.0, "end": 4.2, "text": "첫 문장입니다. " }` 형태의 행 목록

`start`와 `end`는 녹음 시작부터의 초다. 시간이 없으면 둘 다 `null`이다. 모든 행의 `text`를 순서대로 합치면 공백까지 원문과 정확히 같아야 한다. 파일은 기존 JSON과 같은 8 MiB 한도를 따른다.

읽는 쪽은 녹음·오디오·처리기 식별자와 원문 해시, 전체 텍스트 범위, 시간의 유한성·순서·녹음 길이를 검증한다. 선택 파일이 없거나 잘못된 경우 기본 전사 결과를 계속 표시한다. 결과와 시간 파일의 도착 순서가 달라도 다른 원문의 시간을 표시하지 않는다.

Mac은 기존 `TranscriptDisplay`의 문장 분할과 실제 정렬 구간 대응을 재사용한다. 정렬 실패나 텍스트 불일치에는 시간을 보간하지 않는다. 동일한 결과를 다시 게시할 때도 시간 파일을 추가할 수 있어 기존 완료 녹음의 재전사가 필요하지 않다. Mac과 Android가 같은 처리기 폴더에 연결되어 있어야 한다.

Windows의 시간 파일 생성은 이번 Android/Mac 적용 범위에 포함되지 않는다. Windows에서 받은 기존 결과도 문장 구분으로 읽을 수 있지만 시간 표시는 해당 처리기가 실제 시간 파일을 제공해야 한다.

## 확인 범위 (2026-10-18)

Mac build 33과 Android versionCode 16을 설치했다. Android 단위 검사 70개, 에뮬레이터 문장 표시·탭·선택·재생 위치 이동 검사 2개가 통과했다. Mac은 CLT 환경에 XCTest가 없어 독립 assertion harness로 관련 테스트 51개와 기존 전사 표시 검사 23개를 실행했다.

별도 합성 한국어 녹음으로 Mac → Google Drive → Android의 시간 파일 수신·저장·재읽기를 검증했고 9개 문장 모두 실제 정렬 시간이 보존됐다. 초기 Google 재승인 필요 상태는 사용자의 재승인 후 해소되어 같은 폴더로 검증했다. 에뮬레이터 창은 화면 제어 도구에서 인식되지 않아 시각적 비교 완료로 주장하지 않는다.

첫 화면 테스트는 글자 자체에 클릭을 전달해 부모 녹음 행이 열리지 않았고 자동 동기화가 다음 테스트와 겹쳤다. 테스트가 실제 클릭 가능한 행을 선택하도록 수정하고, 테스트 중에만 기존 동기화 gate를 사용해 합성 녹음이 동기화되지 않도록 격리한 뒤 재실행했다. 사용자 계정 설정은 바꾸지 않았다.
